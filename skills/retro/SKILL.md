# Retro

Ретро смотрит назад. Сначала полностью закрой разбор недели, только затем переходи к `planning`.

## Граница

Работай с задачами этого штаба: `TASKS.md` и `tasks/<slug>/`. Результаты в отделах только открывай по ссылкам из задач, сами отделы не обходи.

Источник истины — `task.md` и его журнал. HTML-отчёт — датированное представление недели. Решения по задачам записывает `manager`, а не этот скилл.

## Этап 1. Собрать факты

1. Определи календарную неделю (ISO, `WNN`) и её даты.
2. Прочитай `TASKS.md` и все `tasks/*/task.md`.
3. Включи задачи, у которых в пределах недели:
   - появилась запись в `## Журнал`;
   - поменялся статус или задача заведена;
   - задача ушла в «Готово».
   Добавь открытые задачи, перенесённые с прошлой недели, даже если по ним не было записей.
4. Для каждой задачи возьми из журнала: что сделано, как проверено, что не сделано, ждёт ли владельца, следующий шаг.
5. Для ссылки на результат проверь только, что путь существует. Не выдумывай содержание недоступного результата.
6. Если есть план прошлой недели `reports/ГГГГ-WNN-plan.html`, сверь: какие выбранные результаты стали правдой, какие нет.
7. Покажи полный недельный срез до выводов.

Если записей в журналах за неделю нет, остановись: фактов для ретро недостаточно. Не реконструируй неделю по памяти чата.

## Этап 2. Решить незавершённое

Для каждой задачи `в работе` или `ждёт меня` нужно одно явное решение владельца:

- продолжить — с одним конкретным следующим шагом;
- уменьшить — переписать ожидаемый результат и критерии;
- оставить `ждёт меня` — с конкретным блокером;
- снять — задача больше не нужна: по слову владельца она уходит в «Готово» с записью в журнале «Снята: <причина>».

Не переноси задачу автоматически только потому, что неделя закончилась.

Каждое решение передай `manager`: он пишет запись в журнал задачи и меняет статус в `task.md` и `TASKS.md`.

## Этап 3. Интервью

После показа фактов задавай по одному вопросу:

1. Что повторно помогало доводить задачу до результата?
2. Что повторно мешало или создавало лишнюю работу?
3. Какое одно изменение правил в `AGENTS.md` подтверждается несколькими случаями?

Не спрашивай о том, что уже записано в журнале или видно по ссылке на результат.

Если повторения нет, `AGENTS.md` не меняй — запиши наблюдение только в отчёт. Перед изменением правила покажи точную формулировку и получи явное решение владельца.

## Этап 4. Сохранить отчёт

Создай самодостаточный HTML:

```text
reports/ГГГГ-WNN-retro.html
```

Отчёт содержит:

- период;
- полный срез задач со ссылками на `task.md` и результаты;
- что из плана прошлой недели стало правдой, если план был;
- решения по незавершённым задачам;
- повторяющиеся успехи и помехи;
- принятое изменение правила или отметку, что изменения нет;
- место для ссылки на план следующей недели.

Семантический HTML, встроенный CSS, без сборщика и внешних загрузок. Читается на широком и узком экране.

В шапке:

> Исторический срез недели. Текущее состояние — в задачах `tasks/`.

## Этап 5. Проверка и приёмка

Проверь:

- число задач в отчёте совпадает с недельным срезом;
- у каждой задачи `готово` есть ссылка на результат;
- каждое решение по незавершённому записано `manager` в журнал задачи;
- статусы в `task.md` и `TASKS.md` совпадают;
- факты отделены от выводов;
- изменение правил подтверждено владельцем;
- каждая относительная ссылка отчёта открывается;
- в отчёте нет ключей, паролей и личных данных людей.

Открой отчёт владельцу. Ретро завершено после его приёмки. Затем предложи `planning`.

## Запрещено

- начинать `planning` до принятого ретро;
- выполнять задачи во время ретро;
- скрывать незавершённое;
- менять правило по одному случаю;
- исправлять состояние только в HTML;
- писать в `TASKS.md` и `task.md` в обход `manager`;
- копировать в отчёт содержимое результата вместо ссылки.
